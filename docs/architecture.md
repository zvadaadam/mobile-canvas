# Architecture

## One project, one runtime

`src/runtime/project.ts` owns the strict `expo-canvas.json` document and the command executor; `src/shared/model.ts` defines its public contract. The native canvas, the CLI and the stdio MCP server call the same loopback HTTP service (`src/runtime/server.ts`). A project-local PID lease prevents two runtimes from mutating a project independently, and the runtime is discovered through the explicit project directory, never through global last-opened state.

Opening project data generates an import registry and starts source watchers; it does not execute native code. `open` and `studio open` explicitly launch the signed iOS-on-Mac host and its Metro through `src/runtime/host/launch.ts`, which preflights the bundle so dependency failures surface as errors before a window appears and which tolerates slow runtime answers rather than ending the session. `studio open --screen` records a screen to reveal; once the host reports its first layout, the runtime sends it a focus command that centers and fits the whole frame, accounting for the inspector and title.

## Authoring model

The document holds an ordered list of screen IDs and a normalized map of screen records. A screen is a component source/export plus props, canvas geometry, optional device safe-area `insets`, notes and navigation `links`. The document may also carry `resolver` (import aliases and module substitutions Metro applies to project code) and `origin` (an imported app's path, mode, commit and, for copies, per-file source hashes). IDs survive renaming and reloads; semantic keys are unique and support navigation from components.

An agent command carries `workspaceId`, `sequence`, `requestId`, a label and a bounded list of typed operations. `screen.create` assigns IDs and returns a key-to-ID map; `source.write` requires the SHA-256 from the source read, or null for a new file; `resolver.update` edits aliases and module mappings. Stale writes fail and are never rebased. Replaying an identical request within the session returns its receipt.

All operations are validated before a write-ahead journal is persisted; source files are written atomically and the manifest last; an interrupted journal replays on open. Undo and redo restore the complete source-and-screen transaction and refuse to overwrite external source changes. Source reads reject symlinks and traversal, and bytes and file counts are bounded. Project code runs with Metro's ordinary local privileges once explicitly started; this is a trusted local development environment.

`src/runtime/arrange.ts` computes the flow layout (`/api/arrange`): the unlinked screen that reaches the most of the app is the entry, each linked screen sits one row below the nearest screen that opens it, columns follow the parents, rows are centered, and design variants (same source as a linked screen, linked from nowhere) form a band below. The host's Arrange button, the CLI and MCP apply it as one transaction.

## Existing apps

`src/runtime/adapters/expo/import.ts` plans an import: it resolves the app's `@/` alias from its tsconfig, lists Expo Router routes, walks the source and classifies every bare specifier as `host` (the native host serves it), `app` (a JavaScript-only package of the linked app), `project` (copied) or `missing`. In linked mode nothing is copied: `origin.mode` is `linked`, the alias points at the app's own source root, and `resolver.modules` keys that are app paths override or add files in place. Without `--link` the source is copied into `lib/` with provenance.

`src/runtime/origin.ts` reviews the experiment against the app: `originDiff` returns unified diffs for overrides and added files with the app path each would land on, marking `lib/canvas/` and `lib/shims/` as canvas-only; `originApply` copies chosen files to those paths, refuses a file whose origin changed since import unless forced, and never deletes. `doctor` reads that review to list `diverged`, `added` and `canvasOnly` files.

`src/runtime/adapters/expo/frames.ts` provides deterministic static route analysis. `import` with `link: true, map: true` creates native metadata cards, inferred content links and initial arrangement in the import transaction. `--app` chooses a separate project by canonical app path and bootstraps it through the same loopback import endpoint for CLI and MCP. No app source executes during mapping. With `preview: true`, import instead generates lazy route entries and records `appPreview` in the document; CLI/MCP `--app` enables this for Expo 56 and 57. Source-only mapping keeps the explicit metadata cards. See [drop-in mapping](drop-in.md).

## Native rendering

`apps/native-host` supplies the Expo 54 renderer: one shared React host and one Fabric surface per screen. `packages/native-canvas` supplies the shared UIKit window/frame shell, pointer input and CLI/MCP control/capture. [The native canvas](native-canvas-host.md) records tested behavior and fidelity limits.

`apps/native-host/metro.config.cjs` resolves project code against the host's installed packages and the project's own `node_modules`, applies the project's aliases and substitutions to project files only, and rejects a bare import that would resolve into another SDK. For a linked app it also watches the app directory, applies app-path overrides after resolution (so relative imports are overridden too) and as a fallback for files the app lacks, and lets the app's JavaScript-only packages resolve from its own `node_modules` while refusing its native ones. Because Metro caches resolutions per origin directory, a shim that wraps the module it replaces lives alone in its directory or imports a subpath.

`src/runtime/host/matched.ts` prepares a separate, cached Expo 56 or 57 host for linked app previews. It preserves Bun/npm lockfiles and declared Bun patches while installing matching dependencies and compiles the same Swift shell with one React Native factory per frame. `apps/linked-host` supplies the actual Expo Router root, generated route context resolution, protected-route preview transform, and real SQLite storage isolation. The original app source remains linked and receives no writes; native local modules are copied only as build inputs.

Explicit `--offline` / import `offline: true` records a design environment in `appPreview`. Reusable host adapters disconnect supported Clerk, Convex, RevenueCat and Observe integrations while retaining the app's components and local data. Authentication settles signed out; no user records, purchases or backend results are invented. Public Hugeicons stroke icons can replace declared Pro packs, with the difference disclosed in screen receipts. The window title and MCP state identify design preview. External JavaScript fetch/XHR requests are rejected; native modules are not a network sandbox. MMKV 4 factories use frame-specific IDs. Expo font registration is serialized and shared in the generated dependency so one root cannot unregister a font another is measuring; changing an already loaded font's bytes requires reopening the host.

`packages/preview` exposes disposable mock state and navigation by screen key to components; the host gives each mounted screen its own provider.

## Human canvas

The native shell separates its protocol, state and views. `CanvasRuntimeClient` owns cancellable loopback requests and typed response decoding, shared by the shell and Swift frame reports. Decoding runs off the UI executor; callbacks return to `MainActor`. `CanvasWire` decodes stable session/screen/command fields with `Decodable`, checks document identity/order and geometry, and preserves flexible app props as `CanvasJSON`. Wire models explicitly opt out of actor isolation so imported targets can use either default isolation mode. Renderer integrations and the props inspector retain a Foundation dictionary bridge; they do not define another document model. Zod remains authoritative for runtime mutations.

`CanvasSessionState` is a view-independent projection of the runtime session. It rejects older document sequences and other workspace identities; read tokens keep delayed polls from overwriting a newer local selection. `CanvasSession` owns polling and serializes selection writes, coalescing intermediate clicks so the final focus cannot arrive at the runtime before an earlier click. Failed reads keep the current screens visible; the next successful poll reconciles them. Requests are not implicitly retried as mutations.

`CanvasFrame` owns frame mounting and disposal; `CanvasViewport` computes fit/focus positions without views, and `CanvasCamera` owns the interruptible display-link animation. `CanvasStyle` holds shared tokens. These are shared native sources, not separately published services or additional state stores. The TypeScript runtime remains the only document/transaction authority.

`CanvasController` (in `packages/native-canvas/Sources/CanvasHost.swift`) arranges and selects frames, exposes history, creation and screen navigation, and manages the inspector in the same window. Each frame is a body view with a name above it; the name selects and drags, and fonts and borders are counter-scaled so they read the same at every zoom. Flow connectors are drawn on the board beneath the frames from each screen's `links`, with the selected frame's edges highlighted and a live navigation pulsed. Frame windows are clipped to the canvas viewport so they cannot cover the toolbar or inspector. A status bar reports readiness from the runtime's receipts.

`CanvasInspector` edits name, position, props and context through the canonical transaction endpoint, and reads source, duplicates fixtures, resets a frame and shows the exact CLI/MCP setup. Drafts keep their original identity; a concurrent agent edit cannot silently overwrite a human draft.

## Boundaries

- `src/shared`: schema and types; no filesystem or process imports.
- `src/runtime`: files, executor, HTTP, CLI, MCP, import and review, host launch and build.
- `src/runtime/adapters`: language-specific source/dependency analysis and Swift build preparation; Expo and Swift feed the same project executor.
- `packages/native-canvas`: shared Swift canvas shell, resource assets and separately compiled ScreenCaptureKit fallback. It contains no React integration.
- `apps/native-host`: the Expo 54 iOS-on-Mac renderer, Metro config and generated host template; `apps/linked-host` supplies SDK-matched app integration, and `apps/swift-host` supplies Swift rendering.
- `packages/preview`: component-facing mock state and navigation hooks.
- `designs/*`: portable authored projects, not host implementation.

The repository has no accounts, credentials, paid generation, cloud synchronization, generic graphics nodes or workflow graph.

`host/canvas-template.ts` is the shared native input boundary: Expo builds stage it into their existing generated `native/` and `assets/` layout; Swift builds read the source bundle directly. Generated Expo copies are not additional source of truth. Shared resources participate in native fingerprints, so changing a font or wordmark invalidates the Swift binary too. [Contributing](../CONTRIBUTING.md) maps the entry points and explains public versus private validation.

### Linked route identity and examples

A linked frame owns one source route, with shared navigator contexts recorded as aliases in `props.route.contexts`. Preview-only Babel instrumentation observes concrete links during rendering; the runtime selects available examples deterministically and fills missing params through the canonical command executor, preserving undo and authored parameters. Missing examples have a visible waiting state.

The matched host adapts Expo Router’s action handler: it computes the proposed navigation state using the real router, resolves its URL, and sends a canvas navigation request before a changed route is committed. The destination frame receives requested params through a transaction and is focused by the Swift host; the source remains on its assigned route. Native tabs receive their normal state/provenance update so their selection returns to the assigned tab. Local state controls remain native. `canvas_route_map` exposes the sitemap and `canvas_read_route_source` reads original TSX or its active override without writing to the app.

Screen focus uses a 220 ms interruptible viewport animation (instant for keyboard commands and Reduce Motion). Native frame windows reuse their clip masks and update geometry only when it changes; document polling reconciles layout only after a document sequence change. New React roots mount after camera motion settles. `canvas_inspect_screen` uses the same focus command, waits for the host to settle and a current screen receipt, then requests an authored-size 2× native frame image. Its ephemeral presence is included in host reports: a dashed blue ring and label while capturing, then a brief “Captured for agent” fade. Inspection carries identity checks, never edits document history, and fails if human focus moves elsewhere.

## Visual steps and preview coverage

A route is not necessarily one design. `src/runtime/adapters/expo/pagers.ts` recognizes a deliberately narrow finite pager: an ordered literal list, imported page registry, selected/visited index state, matching ref/animation initializers and a forward transition. It emits stable `route.step` frames without evaluating app code. The linked preview transform seeds those hook slots per frame and redirects the pager transition to canvas focus before it changes local state. Ordinary fields and native controls stay interactive. No app-specific source or fixture is generated. Unrecognized state machines remain unsplit; this is not exhaustive state exploration.

Arrange places each recognized sequence in its own horizontal band between its detected incoming screens and its completion destination. Flow links include each page's detected content destinations and the next step; Back controls are not edges. Source evidence accompanies inferred links. A `canGoBack` / `back` / fallback `replace` branch is excluded from content flow. `src/runtime/adapters/expo/guards.ts` additionally recognizes finite Boolean `Stack.Protected` gates with literal screen names. It records conditional forward eligibility changes and observes the relevant values in the native preview, so an onboarding completion can focus Home while its source frame stays pinned. Initial observations never navigate; changed scalar inputs allow repeated completion. Unsupported expressions, ambiguous entries and explicit initial-route policies are left unresolved. This is not proof that authentication or a service action succeeds offline.

`canvas_route_map` separates visual-frame, source-route and pinned-step counts and explains coverage limits. `canvas_read_route_source` and the native View source action read the selected step component when one exists. The inspector preserves generated route metadata but omits it from editable preview props.

The linked bundle observes returns from default function declarations in mapped route files. A null/boolean output gets a `needs-state` receipt and an explanatory canvas placeholder that disappears when output becomes available. Nested callbacks are not observed. Re-exported, arrow or child components are not yet covered by this return detector. A non-null element does not establish visual or data completeness. The footer reports running frames and detected missing state/parameters, not that every screen is fully populated. Design preview explicitly identifies isolated local data and disconnected services; parameters do not transfer another frame's provider state.

## Preview failures and compatibility

Unavailable service UI and detected missing route state use a centered, muted native card with decorative translucent shapes. Those shapes are generic placeholders, not an inferred image of the app. Frames retain their identity, context and flow links.

In isolated linked runtimes, an uncaught JavaScript interaction error is reported on its frame and replaced by a retryable preview error card. Render boundaries use the same card. A frame error makes studio state `degraded`, with `screenErrorCount`, while healthy frames remain inspectable; host/launcher failures remain session errors. The shared Expo 54 runtime cannot safely attribute a global exception to a frame, so global interception is limited to isolated runtimes. Disconnected speech emits asynchronous error/end events instead of throwing from Resume.

`tests/compatibility/apps.json` pins Clarity, Hot Chocolate and Workout revisions. `npm run test:compat` tests deterministic mapping, stable re-import, required/forbidden edges, unique frames and arrangement. `npm run test:compat:native` also inspects opened Hot Chocolate and Clarity native experiments through actual MCP and saves captures for visual review. Workout is source-only; the curated SDK 54 export was removed. Test apps and generated projects stay under gitignored `.context/`, with upstream URLs and revisions in the corpus. See [compatibility workflow](compatibility.md). Launchers reserve Metro ports across concurrent canvas processes, including IPv4/IPv6 availability checks.

Known native recovery limitation: the SDK 57 multi-runtime host can crash in Fabric scheduler teardown when Fast Refresh falls back to a full reload. This reproduced while replacing and undoing a component export. Frame Retry works; it is distinct from full native reload. Reopen the canvas after this process-level failure. A JS boundary cannot contain a native segmentation fault.

## Developer packaging and prerequisite checks

`npm run package` produces a local npm tarball with an explicit file allowlist: runtime/CLI/MCP source, preview hooks and native host templates/assets. Runtime TypeScript and tsx dependencies install with production dependencies. Experiments, captures, generated native projects and credentials are excluded. `npm run test:package` installs that tarball into a fresh prefix outside the checkout and verifies the executable, actual MCP transport, source-only mapping and environment checks. It does not certify a native build on another Mac.

`src/runtime/environment.ts` owns read-only prerequisite diagnostics. `expo-canvas setup` works before a project exists; `canvas_environment` calls the same report through `/api/environment` for an opened project. A cold linked-host launch checks requirements before installing/building. Checks never install software, accept agreements or configure accounts. Manual provisioning and render validation remain explicit. This is the prerequisite adapter for a future first-run UI, not a separate human application; the native canvas remains the human surface. See [distribution](distribution.md).

Installed npm packages are treated as immutable. `installation.ts` locates per-user signing settings, shared build/capture caches and the authored host; source checkouts retain their development host paths. `setup` provides readable CLI diagnostics (or `--json`), optional Team ID entry, and explicit frozen dependency installation with `--install`. MCP retains the same read-only environment report. `build` prepares the installed SDK 54 host from its packaged lock snapshot. Linked host templates become writable only in the generated project, preserving read-only installations. Native package acceptance tests exercise fresh builds and warm reopen through the installed MCP executable.

Generated native copies normalize writable template permissions. Build preparation quotes Expo Constants script paths, escapes local React Native prebuilt artifact URLs, and the host plugin exits the unused JS bundling phase when `SKIP_BUNDLING=1`, supporting project paths with spaces. Config-plugin changes force prebuild rather than an incremental Swift-only rebuild. Native wrappers built under macOS temporary directories launch from a stable per-user cache, preserving the relative WrappedBundle symlink; build inputs and source remain in their original locations. Capture helpers are cached by source hash so npm archive timestamps cannot hide an updated helper.

## Canvas navigation and setup ergonomics

The native screen navigator is a searchable document index in `CanvasInspector.swift`. Its callbacks use the controller's existing selection and camera path, so human and agent focus stay shared. Panel layout reserves space on both sides; a non-key, pass-through tools window sits above independent native frame windows for canvas controls. Camera fitting reserves bottom clearance for the tools. Search and panel toggles are view state, not document mutations.

`project-context.ts` detects only the current directory's Canvas manifest or Expo package dependency without evaluating application code. Explicit CLI paths win. Setup can reuse one unambiguous local development team: `signing.ts` matches public certificate fingerprints to valid signing identities and extracts the Team ID from the subject OU. Multiple teams require a choice; no identity labels or private keys are stored. JSON diagnostics do not auto-save a discovered team.

## Proposed Swift support

[Native adapters](native-adapters.md) records the original proposal to extract the Expo implementation behind project/build and native frame boundaries, then add SwiftUI/UIKit iOS projects. The experimental implementation and its current limits are described below; the proposal's staged acceptance criteria are not all complete.

## Experimental Swift adapter

`src/runtime/adapters` selects the renderer/build path without changing the canvas command loop. `CanvasRendering` owns the native content controller and frame lifetime; the common UIKit shell owns geometry, inspector, navigation focus, readiness and capture. The Expo renderer retains its existing React factories. The Swift renderer hosts supported `#Preview` expressions in independent SwiftUI hosting controllers, with a `CanvasPreviewContext` for props and explicit canvas navigation. Swift projects use version 2 documents with `nativePreview` input membership and app-relative overrides. Source edits compile and relaunch a generated iOS-on-Mac target; native version receipts prevent old binaries from passing inspection. Swift globals/services are shared and not sandboxed.

Swift discovery reads Xcode target membership and runs a SwiftSyntax scanner without executing the app. Screen discovery is independent of preview construction: root composition, named navigation destinations, value-based registrations, recognized coordinator callbacks, sheets/fullscreen covers, and switch-selected panes produce a source-backed graph. Link evidence includes the file, line and navigation kind. Single-expression wrapper previews can supply a canonical destination; unmatched component previews remain separate. Missing factories remain visible as unavailable cards with requirements and destination buttons. This is bounded syntax analysis, not whole-program type resolution or an exhaustive list of runtime states. Conditional alternatives are potential paths; method-name resolution is conservative only where the names are unambiguous. UIKit navigation, custom routers, type-erased destinations and arbitrary state machines need further integration.

Re-import preserves existing IDs, authored notes and placement, replaces only previously generated links, and refreshes Xcode target membership in the same undoable transaction. `native.refresh` checks the project-file hash and refuses a changed target. `native.override` checks the original source hash; the original app remains read-only. Newly added source files require re-import. Generated builds remove only the app’s `@main` attribute, retaining its type, extensions, sibling views and resources without instantiating the original app. A shared preview compiler feeds either a lightweight system-framework target or an isolated target derived from the app’s Xcode configuration. See [Swift build adapters](swift-xcode-builds.md) for the module boundaries and supported package/Metal inputs.

The Swift catalog supports up to 128 frames; Expo retains its 32-frame limit. The MCP sitemap distinguishes discovered destinations, registered factories and missing preview data. Catalog destination buttons and explicit `CanvasPreviewContext.navigate` move canvas focus; ordinary Swift app navigation still runs locally and is not automatically pinned. A registered factory does not establish visual completeness or backend availability. The preview execution and map coverage limitations must remain visible until those capabilities are implemented and tested.

Xcode source discovery can also map targets with unsupported local packages, target dependencies, mixed-language sources, custom framework references and build phases. These requirements are stored as `nativePreview.buildIssues`. When present, open builds only the native catalog shell: no app sources, resources, package code or app build phases are compiled or executed. Every destination is marked `build-integration`, executable factories are withheld, and MCP reports `liveAppPreview: false`. Unassigned component-preview variations are returned in the import's `unmappedPreviews` inventory rather than duplicating unavailable cards in the navigation map. If there are no flow destinations, preview declarations remain the catalog. This is source-map support, not native app rendering support.

Inspection activates the requested experiment's existing native window before capturing and requires a screen receipt after activation. iOS-on-Mac may otherwise retain earlier pixels while background model receipts continue to arrive. This shared runtime behavior applies to Swift and Expo, and intentionally brings the inspected canvas forward.

### Automatic Swift preview recipes

`adapters/swift/recipes.ts` derives render recipes from source independently of the screen graph. It can construct supported default views, follow an existing child constructor inside a demo/preview view, bind required inputs to typed values owned by an app-local demo (including protocol-extension collections), and expose computed sheet content. Generated Swift keeps the state-owning parent mounted and selects a child through an environment path, retaining SwiftUI state storage. It never edits the imported app or checks an app-specific shim into the product. Generated code lives only under the experiment's build directory.

The analysis is deliberately bounded and heuristic. Demo/preview names identify potential local fixture roots; inputs prefer matching names/types, supported action callbacks become inert, optional inputs may be nil, and an `isActive` pane input can be enabled. A missing collection example displays an unavailable state rather than being force-unwrapped. Supported `ForEach` element bindings and `if let` scopes can be reconstructed around a child constructor; unknown closure parameters and local computations remain excluded. Required SwiftUI environment objects are followed through visible composition and modifiers; supported default constructors get per-frame storage. Their transitive singleton services are **not** disconnected or isolated. Provenance is exposed in screen metadata, notes and MCP receipts.

Mapping does not run app code. Native code executes only on explicit open. Neither this syntax analysis nor a successful native build proves that every initializer is free of side effects, every screen is populated, or every app dependency is supported. Unsupported Xcode target graphs and custom build phases remain explicit blockers. Navigation pinning, arbitrary record synthesis, arbitrary state machines, private cross-file construction and full service isolation remain incomplete. Swift validation includes DEUS, BetterMind and focused regression fixtures; Expo compatibility tests do not establish support for other Swift apps.


Automatic Swift recipes also follow bounded nested model paths and optional collections, respect private getters, and prefer non-optional examples before guarded alternatives. Binding and constructor propagation repeat so a newly renderable parent can supply its descendants. Extraction retains outer `task`, `onAppear`, `onDisappear`, and `onChange` modifiers in the projected branch only; the original branch retains its own modifiers. This preserves app-authored loading behavior without mounting an invisible duplicate of the original screen.

Complete typed owner bindings are committed before optional record guesses. This lets a list owner supply its detail through its own loading lifecycle. Source constructor alternatives rank by the number of guarded bindings and then owner-path length, with stable source order breaking ties; cycles are rejected. Recognized lexical bindings live in `projection.ts`, separately from recipe selection. This is static selection, not runtime search through every record or fallback recipe. See [preview state resolution](preview-state-resolution.md) for the shared architecture and language-specific limits.

An accessible, unique Demo/Preview implementation of an initializer’s service protocol can replace its default when no existing constructor recipe is available. Known UIKit control return types (such as `UIPasteControl`) do not by themselves block a default SwiftUI preview; unconfigured native controller compositions still require setup. These are construction rules, not service isolation or a guarantee about initializer side effects. Missing factories carry a structured blocker (`inputs`, `lifecycle`, `native-bridge`, `generic-content`, `environment`, or unsupported composition/body) in the manifest and MCP sitemap. A factory whose selected collection is empty remains unavailable at runtime.

`tests/fixtures/swift/RecipeLab.swift` is an ordinary, self-contained Swift test app with no Canvas hooks or preview registrations. Its native acceptance run covers asynchronous parent data, nested detail extraction, an app-local service and a UIKit control. It supplements DEUS and scanner regressions; it is not evidence of arbitrary Xcode-project support. The Swift launcher identifies its native process by exact host ID before relaunch, including when a rebuild starts before the first host receipt.

The Xcode strategy separates service readiness from compilation. The default isolated context records conservative `app-startup` requirements. Explicit application context instead initializes and retains the original SwiftUI App once, while Canvas retains ownership of the window and delegate lifecycle. An unambiguous app-authored preview provider may repair missing typed environment state, with provenance. This does not supply credentials, execute App.body or isolate globals. The shared Mac motion capability adapter reports device motion unavailable rather than starting a virtual sensor. BetterMind's current native pass captured 75 frames: 66 mounted factories, 9 explicit requirements, with blank and partial states reported separately. See [the build verification and limits](swift-xcode-builds.md).


### Composed Swift states

`adapters/swift/scenes.ts` selects supported finite states through an existing parent preview rather than extracting a bare child. `CanvasSceneSelection` preserves the authored parent body and its styling; state metadata records the owner, selector, case and destinations. Repeated child types can represent distinct states. Native state families use compact arrangement bands. Supported selector changes request canvas navigation and restore the pinned case; arbitrary navigation and shared model changes remain outside that mechanism. See [composition limits](swift-xcode-builds.md#parent-composition-and-external-actions).

The Swift host disables MessageUI mail capability before app initialization and discards SwiftUI `openURL` requests per frame, reporting redacted blocked-action metadata. The original app is unchanged. This prevents the reproduced feedback preview from opening an email composer, but does not sandbox native code or network activity.

### Native component catalog and local images

`adapters/swift/catalog.ts` provides a read-only inventory of app-authored previews, animation API evidence and bundled image assets. CLI `previews` and MCP `canvas_native_preview_catalog` use the same loopback endpoint. Explicit `swiftPreviews` import choices create component frames separately from source navigation; their selection lives in existing screen metadata and survives re-import. Arrange groups them in a component band.

The Swift compiler can attach a frame-local image context to supported Kingfisher calls in app SwiftUI bodies. `apps/swift-host/PreviewImages.swift` supplies a named bundled asset only when that frame has an explicit `native.imageFixtures` mapping. Processing and layout stay app-authored, missing assets are reported, and other loaders remain unchanged. This helper is conditionally compiled when Kingfisher is present, adding no package dependency to other Swift apps. See [native preview catalog](native-preview-catalog.md) for commands and limits.

The same Swift surface pass scopes supported `UIScreen.main.bounds` reads to `CanvasPreviewContext.bounds`, updated from the frame dimensions. It covers struct bodies and representable make/update methods; globals and arbitrary helpers keep their original behavior. This corrected an oversized RemoteMessageDetailView layout while retaining its original image processing and text. Native SceneLab checks verify different widths in two frames after a size edit.

Native source watching follows declared target inputs, including Metal, asset contents, property lists and package resolution files. Missing files invalidate the binary without preventing the project from opening or refreshing target membership; native builds still reject missing required inputs. Commands and both import adapters share the project store's request receipt cache, so a retried import returns its original result without duplicating frames or weakening sequence checks.
